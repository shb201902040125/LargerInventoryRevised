# LargerInventory 后端实现说明（v0.7）

## 执行和保存

- `InventoryStore` 接收命令，`InventorySystem.PostUpdateEverything` 在主线程推进执行与修复。页加载、游戏物品序列化和仓库状态发布都在主线程进行。符合并发条件的槽位操作及其堆叠钩子可能在工作线程运行。主线程为脏页准备字节快照，实际保存线程在执行锁下提交快照。
- `StoreRedoJournal` 暂存页、备份、`store.meta` 和联机事务记录。完整暂存目录改名后构成提交点，随后逐个发布文件。发布中断时先重放日志，再开放仓库访问。页和元数据均使用 v2 格式。旧测试格式不会迁移。备用 `store.meta` 可能较旧，首次推进会按页核对索引。
- 角色仓通过实际 `Player.SavePlayer` 保存。世界仓和服务端个人仓接入世界保存，服务端也定期刷新。未完成的仓库提交会记录错误，等待重试。

## 指令与修复

- `Command.InputPayload` 和 `CommandResult.ResultPayload` 分开。Put 只有在整笔物品都能放下时才提交。空间不足时回滚本次的槽位变更并归还全部输入。Take 返回实际取出的物品，调用方负责交付。强指定操作限定在请求的槽位，不能移入异类占用的目标。失败页保留页号并移出可用物品索引。
- 执行器按批次持有页的共享使用权，每条命令结算后释放其槽位预留。强指定预留声明的槽位，弱指定先在批次已持有的页内寻找，仍有缺口才按估算容量降序选页，同容量按页号升序。冷页用摘要估算，实际操作仍检查物品与模组堆叠规则。
- 批次内，连续的小型强指定指令可并发执行。冲突判断使用两个 64 位槽位掩码，默认每组 4 条、每条 16 槽。同槽双读可以并发，涉及写入的哈希碰撞保守串行。每组按 FIFO 发布实际槽位变更。普通命令和并发波次共享待刷新页集合，在类型查询、弱指定和批末捕获快照前统一更新摘要及索引。调优参数及其影响见 [StoreConfig.cs](<StoreConfig.cs>)。
- `Label` 和 `Br` 通过 `BranchLabel` 引用严格一一配对，在同一次 `PushBatch` 提交。交叠区间合并后整体出队，内部 `Boundary()` 作为空操作。受保护区间串行执行，`Br` 在此前已执行的指令结算后求值，返回 `true` 就跳到对应 `Label`。区间长度和执行步数分别受 `MaxControlFlowCommands`、`MaxControlFlowSteps` 限制。
- `Br` 通过 `BranchContext.TryGetResult` 读取区间内最近一次执行的结果，通过 `Command.Result` 读取此前已结算的批次。Take 的批内结果携带当次取出件数，最终交付累计物品。Put 再次访问时只处理尚未移交的输入。回调按入队顺序结算一次，正常结束时未访问的命令结算为 `Skipped`。
- `PushControlTransaction` 将整个事务压入一个执行批次。`TransactionAction` 显式创建或恢复保存点，恢复槽位、页分配、批内结果和物品归属。事务结束后 `settle` 读取 `ExecutionStatus` 并决定 `Commit` 或 `Rollback`。结算回调抛异常时恢复入口状态。事务内 Escape 使用隔离副本，背包交付和世界掉落由调用方安排在提交后。这里的提交确认内存变更，持久化由仓库保存流程处理。
- `Escape` 和 `EscapeConcurrent` 默认借用物品，引用仅在回调期间有效，原地修改无法回滚。并发借用按写访问判定冲突。可指定 `cloneItems: true` 来隔离修改。普通指令整堆搬运可转移原引用，堆叠与拆分保留保护原物品和失败回滚所需的副本。
- 修复和命令共用执行锁。修复需要独占页，命令只在批次收尾和快照捕获完成后释放页使用权。有效备份可恢复主文件。确认损坏且无可用备份时，先将文件原始字节隔离，再提交同页号的空白页和摘要。读写错误、未知版本及模组物品加载错误保留待处理。修复与暂停限单机。
- 单机取出先合并背包堆叠，再尝试世界掉落，剩余部分可随角色保存。自动拾取接收原版拾取余量。补货按实际缺口和堆叠兼容性选择物品，目标变化时退回余量。

## 联机

- 协议 v7 绑定世界 UUID 与角色 UUID。客户端与服务器需使用同版，取货回执按交付代次校验。每个世界中相同角色 UUID 的连接共享一个个人仓。最后一个连接离开后，空闲约 60 秒且没有在途工作时关闭该实例。重连时从持久状态重开。
- 联机事务和服务端定时保存都在游戏线程准备快照，在后台提交仓库文件。仓库在提交期间返回 `PageBusy`，达到持久化点后由游戏线程完成回调。显式保存与关闭仍可同步收尾。旧页摘要默认每次推进最多校准四页，期间返回 `Preparing`，完成后开放仓库。
- 可恢复的测试事务先保存客户端操作 ID 与序号，重连后查询待处理操作。取货由服务器安排背包发放。只有原计划被证实未应用，且服务端收到匹配会话、交付代次和回包的拒绝后，才会重新规划。发放结果不明时保持待交付。背包发放确认后再处理溢出掉落。
- 可恢复事务的已确认结果可压缩，服务端保留每个角色的已退役序号，客户端收到退役确认后清理回执。当前 GUID-only 事务与带序号事务共用 v4 账本，GUID-only 记录按原操作 ID 去重和查询。
- 测试命令受服务器配置控制，并调用联机事务入口验证流程。后续对外接口应允许上层事务合批提交，保留提交完成与物品交付完成的区别。Put 的物品继续由服务端事务来源提供。
- tModLoader 分别写入背包和模组回执。跨两次保存中断时，结果不明的交付会被保留。复制同 UUID 的角色可以共享仓库，角色文件仍各自保存。

自动化覆盖和游戏内检查见 [人工测试计划](<../MANUAL_TEST_PLAN.md>)。自动化使用隔离目录验证提交重放、页恢复和事务过程。实际游戏物品兼容、多人交付与物理断电后的文件系统行为需单独验证。
